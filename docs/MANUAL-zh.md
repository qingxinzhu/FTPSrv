# FTPSrv — Windows 局域网 FTP 文件共享服务器

单文件 C++17 写的 Windows 原生 FTP 服务器，**一份引擎 + 两个壳**：

| 可执行文件 | 形态 | 适合谁 |
|---|---|---|
| `ftpsrv-gui.exe` | 图形界面（无黑框窗口），带独立设置页 | 一般人 —— **推荐** |
| `ftpsrv.exe` | 命令行/控制台窗口，参数启动 | 习惯命令行、要写成脚本的人 |

两个都是静态链接、**不需要任何运行库/解释器**，双击即用。引擎同一份源码（`ftpsrv_engine.inc`）。

支持两种共享模式：

- **全盘共享**（默认）：把本机所有逻辑盘都开放出去，客户端看到 `C:` `D:` `E:` …
- **单目录共享**：只开放指定目录（`--root D:\share`）

---

## 一、图形界面版（推荐，双击就跑）

把 `ftpsrv-gui.exe` 拷到 Windows 上任意目录，**双击**——没有黑框窗口，是一个小窗：

```
┌─ FTPSrv - 局域网 FTP 文件共享 ───────────────┐
│ 状态：运行中 · 监听 2121 · 已连接 1          │
│ 全盘共享（C: D: … 每块盘都能访问） · 账号 admin│
│ [ ftp://192.168.1.11:2121/        ] [复制地址]│
│ [启动服务][停止服务][设置…][放行防火墙]      │
│ 传输进度（实时速度）：                      │
│ DOWN movie.mkv [####----] 52% 1.05/2.80 GB 84 MB/s │
│ UP   photos.zip    12.4 MB  8.1 MB/s         │
│ ┌ 日志 ────────────────────────────────────┐ │
│ │ [21:48:49] server started: port=2121      │ │
│ │ [21:50:02] connect: 192.168.1.31          │ │
│ │ [21:50:11] DOWN RETR movie.mkv: ...       │ │
│ └──────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

用法就三步：**先点「设置…」改好端口和账号 → 点「启动服务」→ 把地址发给对方**（「复制地址」一键拷走）。

小窗上的东西：

- **状态**：是否在跑、监听哪个端口、当前几个连接。
- **地址栏**：本机所有可用地址（VMware/VirtualBox 那种虚拟网卡也在里面，挑能用的那个发出去就行）。
- **启动 / 停止 / 设置 / 放行防火墙** 四个按钮。服务运行中时「设置」会禁用（改配置要先停服务）。
- **传输进度**：两行，实时速率 + 预计剩余时间，原地刷新不刷屏。
- **日志**：带时间戳的滚动记录（最多保留 800 行），可「清空日志」；同时在 exe 同目录写 `ftpsrv.log`（可在设置里关掉）。

### 设置页（所有能调的都在这里）

点「设置…」弹出独立的一个小窗，分四组：

| 分组 | 内容 |
|---|---|
| **共享内容** | 全盘共享 / 指定文件夹（点「浏览…」选目录） |
| **登录账号** | 账号、密码、允许匿名登录（匿名只能读） |
| **网络与限制** | 端口、最大连接数、空闲超时（秒）、首选地址（多网卡时决定显示/复制哪一个）、TCP保活（秒）、**数据端口范围**（默认 50000-50100） |
| **其它** | 只读模式（禁止上传/删除）、记录日志到 ftpsrv.log、启动程序时自动开始服务、**关闭窗口时缩到托盘**（默认勾）、传输完成后强制写入磁盘（默认不勾，见下方说明）、**只允许这些 IP 连**（留空 = 不限制） |

点「确定」保存，配置写进 exe 同目录的 **`ftpsrv.ini`**，下次打开自动带出来。点「取消」或按 ESC 不保存。

「放行防火墙」按钮：如果程序本身已经是管理员权限就直接加规则；否则会请求 UAC 提权（弹一次窗点「是」即可）。它加的是 TCP 端口 + 程序本身 + 一个数据端口段，三种网络配置文件全覆盖。

### 托盘 · 访问控制（IP 白名单） · 程序图标
| 功能 | 怎么用 | 说明 |
|---|---|---|
| **最小化到托盘** | 默认已开。点窗口右上角的 × → 窗口隐藏，**服务继续跑** | 托盘图标：双击 = 打开主界面，右键 = 打开 / 停止 / 退出。不想要这个行为：设置 → 其它 → 取消「关闭窗口时缩到托盘」 |
| **IP 白名单** | 设置 → 其它 →「只允许这些 IP 连」填 `192.168.1.0/24`（可逗号分隔多个，支持单个 IP 和 CIDR） | 留空 = 不限制。**本机回环（127.0.0.1）和本机自己的 IP 永远放行**，所以「复制地址」和诊断.bat 的本机自测不受影响。被拒的连接会记 `rejected (not in allow list): IP`；命令行版是 `--allow` |
| **程序图标** | `icon.ico`（7 种尺寸 16～256）由 `icon.rc` 经 windres 编进 exe | 资源 id = 1，图形版的窗口、任务栏、托盘都用它；同时写入版本信息，任务管理器里显示的是 `FTPSrv - LAN FTP file server` 而不是文件名。两个 exe 都带 |

## 二、命令行版（进阶，可选）

`ftpsrv.exe` 是同一引擎的控制台版本，参数启动，适合写脚本/放计划任务。

---

### 命令行参数

| 参数 | 说明 |
|---|---|
| `--port N` | 监听端口，默认 `2121` |
| `--root PATH` | 只共享指定目录（不写则全盘共享） |
| `--user NAME` | 登录用户名，默认 `admin` |
| `--pass WORD` | 登录密码，默认 `admin` |
| `--anon` | 额外允许匿名登录（匿名 = 只读） |
| `--readonly` | 全部只读（禁止上传/删除/改名/建目录） |
| `--log FILE` | 访问日志同时写入文件 |
| `--idle SEC` | 空闲与传输超时，默认 900 秒 |
| `--maxclients N` | 并发连接上限，默认 64（多线程客户端会同时占好几条） |
| `--keepalive SEC` | TCP 保活空闲秒数，0 = 关闭（默认 30） |
| `--pasv-range L-H` | 数据通道端口范围，默认 50000-50100 |
| `--flush` | 上传完成后强制落盘再回 226（默认关，见 FAQ 第 8 条） |
| `--allow LIST` | 只允许这些客户端 IP 连（如 `192.168.1.0/24,10.0.0.5`，留空 = 不限制） |
| `--addfw` | 自动加 Windows 防火墙放行规则（**需管理员**） |
| `--noprogress` | 不绘制实时进度行（默认绘制） |
| `-h` / `--help` | 帮助 |

示例：

```
ftpsrv.exe --root D:\share --user jack --pass 1234 --log D:\ftpsrv.log
ftpsrv.exe --port 21 --anon --readonly           只读，允许匿名
ftpsrv.exe --addfw                               管理员运行一次，放行端口
```

## 三、传输时的实时速度

传输进行中，控制台底部会出现**一行（最多两行）原地重写的进度**，不会滚屏、不会刷出一屏的历史：

```
DOWN ubuntu...04.iso        [#######-----] 185.00 MB/300.00 MB 84.28 MB/s
UP   photo-collection.zip   6.84 MB 11.28 MB/s
```

- **知道总大小时**（下载；或客户端用 `ALLO` 声明了大小的上传）：进度条 + 已传/总大小 + 实时速度。
- **上传一般没有总大小**（FTP 协议本身不上报，多数客户端不发送 `ALLO`），这行就只有：已传字节 + 实时速度。这是协议限制，不是程序偷懒。
- **没有剩余时间预测**：实测这个数字抖得厉害、还经常预测不出来，索性去掉了 —— 想知道还差多久，用「总大小 − 已传」除以当前速度自己估一下更靠谱。
- 进度行是**原地重写**：连传几个小时也只占那一两行。同时有两个传输就占两行，谁传完那一行立刻消失、下方不留空行。
- 传输结束会留一条带平均速度的汇总日志：
  ```
  [21:48:49] DOWN RETR ubuntu-24.04.iso: 300.00 MB in 12s (25.00 MB/s)
  ```
- 速度是 0.25 秒采样一次再做平滑（新值 35% + 旧值 65%），避免数字乱跳。
- 如果服务器输出被重定向（写进文件/被管道接走，检测不到控制台），ANSI 改写不可用，会自动退化成**每 5 秒一行纯文本**，同样不刷屏。
- 不想要这行：加 `--noprogress`。

### 大文件 / 批量传输的稳定性（几百 GB 也不掉线）

大文件或多文件跑到一半"连接被关闭"，在 FTP 里通常是这四个原因，本版全部处理过：

| 原来的问题 | 现在的做法 |
|---|---|
| **每传一个文件都新建一个被动端口监听**，端口在 TIME_WAIT 里堆积，几百上千个文件后端口耗尽 → 425/426 中断 | 每个会话**只开一个被动监听、整批复用**（同一端口），端口占用从「2 个/文件」降到「1 个/会话」 |
| 数据端口由系统随机分配，**防火墙规则根本没法描述它**（想放行也不知道放哪个端口） | 数据端口固定在设置里的 **数据端口范围**（默认 50000-50100，被占就换一个，整个范围都被占/被系统保留才退回随机），防火墙规则跟着这个范围走 |
| **控制连接长时间空闲**（大文件传输时几小时没数据），被路由器/NAT 悄悄掐断 → 客户端报"连接已关闭" | 控制连接与数据连接都启用 **TCP 保活**（默认 30 秒探测一次），既保住 NAT 映射，也能快速发现真的断了的对端 |
| 默认 64 KB 套接字缓冲，千兆/2.5G 内网跑不满 | 数据连接套接字缓冲提到 **1 MB** |
| 64 KB 一块地读写，系统调用太多 | 传输块提到 **256 KB** |

另外两处细节：上传完成后要不要先 `FlushFileBuffers` 落盘再回 `226`，由设置页「传输完成后强制写入磁盘」控制，**默认不勾**（原因见 FAQ 第 8 条：几 GB 的文件在机械盘上落盘要几十秒，客户端等 `226` 会等到超时）；发送遇到 `WSAEINTR` 会自动重试而不是直接判失败。

**相关设置**（图形版「设置… → 网络与限制 → TCP保活(秒)」；命令行 `--keepalive SEC`）：

- 默认 `30`（秒），一般不用动。
- 路由器/NAT 特别激进（十几分钟就掐空闲连接）可以调到 `15`。
- 填 `0` = 关闭保活（不推荐）。
- 如果批量传输还是断，看日志里最后几行：出现 `425` / `426` 就是数据连接层的问题，把日志发出来就能定位。

### 多线程 / 分段传输（客户端开着「多线程传输」时）

手机上的文件管理器（MT 管理器、ES、部分下载器）有一个**多线程传输**开关，打开后它有两种用法：

| 用法 | 客户端的动作 | 服务器这边的应对 |
|---|---|---|
| **多文件并发** | 同时开好几条控制连接，一个文件一条 | 每个会话一个独立线程 + 独立被动监听端口，默认最多 **64 个并发会话**（超了会回 `421 Too many connections` 并在日志里记 `rejected (max clients)`） |
| **单文件分段** | 把一个大文件切成几段，每段一条连接，前面带 `REST 偏移` | 见下面两条 |

**分段上传（`REST 偏移 + STOR`）**：这是真正会出事的地方——几段是**并发**写的，
谁先连上谁创建文件。如果后到的那条按"覆盖"方式打开，就会把兄弟段已经写进去的数据**截断成 0**。
本版加了并发登记表：**同一个路径只允许第一个到达的连接创建/截断**，后面的统统以"已存在则打开、不截断"的方式写。
日志里能看出来：

```
[22:41:02] STOR 电影.mp4 (192.168.1.13)                          <- 第一段，创建文件
[22:41:02] STOR 电影.mp4 resume=1073741824 (192.168.1.13)        <- 第二段，从 1 GB 处写
[22:41:02] STOR 电影.mp4 (parallel segment, no truncate) (...)   <- 另一段，不截断
```

**分段下载**：FTP 协议里**没有"只发第 N 到第 M 字节"这种命令**，服务器只能从 `REST` 的偏移一直发到文件末尾。
所以每一段拉够自己那份之后，客户端必须**自己把连接掐掉**——服务器这边就会记一条
`aborted after N bytes (socket error 10054)` 并回 `426`。这是**分段的正常代价**，不是故障：
数据没错，客户端拿到自己要的部分就走了（实测 40 MB 的文件单连接完整传完 ✓）。

**如果你的客户端开多线程还是报任务失败**：把它的「多线程传输」关掉，改单连接。多线程省的那点时间，
在局域网里基本感觉不到，但会让客户端自己的重试逻辑变成一场风暴（实测 4 秒内发出 38 条命令）。

### 为什么文件不走 2121 端口？（FTP 天生是两条通道）

FTP 从 1971 年的设计（RFC 959）开始就是**两条 TCP 连接**：

| 通道 | 谁连谁 | 传什么 | 什么时候关 |
|---|---|---|---|
| **控制通道** | 客户端 → 服务器 **2121** | 命令与回复：USER / PASS / PWD / LIST / RETR / 226 … | 整个会话期间一直开着 |
| **数据通道** | 见下 | 真正的文件字节、目录列表 | **每传一次建一条，传完就关**（"关"就是"传完了"的信号） |

数据通道由谁主动发起，分两种模式：

- **被动模式（PASV / EPSV，默认）**：服务器自己开一个监听端口，在回复里把端口号告诉客户端——
  `227 Entering Passive Mode (192,168,1,11,195,88)`，把最后两个数拼起来就是端口：195×256+88 = **50024**。
  客户端随后连这个端口，数据就走在这上面。本程序的数据端口范围**可以在设置里改**（默认 **50000-50100**，被占就换一个）。
- **主动模式（PORT / EPRT）**：反过来，客户端开个端口，服务器从高位端口连过去。现在的客户端默认都用被动模式，主动模式只在被动连不通时才需要试。

所以 `netstat -ano | findstr :2121` 只看得到控制通道；想看数据通道：

```
netstat -ano | findstr ESTABLISHED
```

传输中会看到类似两行（同一个 PID，一个是控制、一个是数据）：

```
TCP  192.168.1.11:2121     192.168.1.31:54312   ESTABLISHED  13360
TCP  192.168.1.11:50024    192.168.1.31:54313   ESTABLISHED  13360
```

传完了数据那一行就消失，2121 那行还留着 —— 这就是"文件不走 2121"的全部原因。

**为什么要这样设计**：数据连接传完就关，"关"这个动作本身就是 EOF 信号；控制连接留着，才能随时发下一条命令、传下一个文件。

**实际影响**：防火墙/路由器必须**同时**放行 2121 和上面的数据端口范围。图形版「放行防火墙」/ 命令行 `--addfw` 会把这两条一起加 —— **改过数据端口范围后要再点一次**，规则才会跟着更新。"能登录成功、但列目录/传文件报 425 / 426"基本都是数据通道被拦。

### TCP 保活保的是哪条连接？

保的是**已经建立的两条连接**（不是监听端口）：

- **控制通道**：客户端临时端口 ↔ 服务器 2121。大文件传输时它几小时不发数据，最容易被路由器/NAT 清理 —— 这条是关键。
- **数据通道**：客户端临时端口 ↔ 服务器 50000-50100 里的某一个。只有客户端中途卡住（比如笔记本合盖、Wi-Fi 抖动）时才起作用。

2121 和数据端口的**监听套接字不需要保活**：它们没有"空闲连接"这回事，NAT 也不追踪它们。

原理很简单：空闲 N 秒后自动发一个空的探测包，让中间设备（路由器/NAT/防火墙）的连接跟踪表一直不过期；顺带如果对端真的没了（手机掉了 WiFi），几个探测失败后我们立刻判定断开，而不是傻等 900 秒超时。默认 `30` 秒，Windows 系统默认是 **2 小时**——对家用路由器来说等于没有，所以必须自己设。

## 四、关于防火墙

首次运行 Windows 可能弹「是否允许此应用通过防火墙」，勾选**专用网络**并允许即可。
如果没弹或连不上，用管理员 CMD 执行：

```
ftpsrv.exe --addfw
```

或手工：

```
netsh advfirewall firewall add rule name="FTPSrv LAN 2121" dir=in action=allow protocol=TCP localport=2121
```

被动模式的数据连接用的是随机高位端口，所以最省事的做法是允许整个程序的入站（`--addfw` 会尝试同时加程序规则）。若网络环境很严，可改用主动模式（FileZilla：站点管理器 → 传输设置 → 主动）。

## 五、安全提示

- 传输是**明文** FTP（不加密）。只在内网/可信任的网络里用，别往公网映射端口。
- 默认账号 `admin/admin` 请务必改成自己的（`--user --pass`）。
- **全盘共享 = 整个电脑的读写权限都给出去了**，比普通共享目录危险得多。建议：
  - 只在家里局域网用，用完关掉；
  - 或者用 `--readonly` 只读共享；
  - 或者用 `--root` 指定一个专门的共享文件夹。
- 服务器跑在当前用户权限下：管理员身份运行时，客户端也能改系统盘里的东西；普通用户身份运行时，权限就限制在该用户能碰的文件里。

## 七、已实现的 FTP 命令

```
USER PASS QUIT SYST FEAT OPTS(NOOP/UTF8) NOOP HELP CLNT
PWD XPWD  CWD XCWD  CDUP XCUP
TYPE MODE STRU ALLO REST
PASV EPSV PORT EPRT
LIST NLST RETR STOR APPE ABOR
DELE MKD XMKD RMD XRMD RNFR RNTO
SIZE MDTM STAT
```

特性：被动/主动双模式、断点续传（REST）、UTF-8 与本地代码页自动协商（中文文件名不乱码）、多客户端并发线程、单连接超时回收、日志带时间戳与客户端 IP、**传输实时速度与 ETA（原地刷新一两行，不刷屏）**。

## 八、常见问题

**1. 连上了但看不到盘 / 列表为空**
第一次进的是虚拟根目录，里面直接列盘符（`C:` `D:` …）。资源管理器里双击 `C:` 就进去了。

**2. 中文文件名乱码**
服务器默认按系统本地代码页（中文 Windows 是 GBK）与客户端对话，资源管理器这类客户端正常。
FileZilla 请手动在「站点管理器 → 字符集」选 **使用自定义字符集：GBK**，或让服务器端跟着走 UTF-8（客户端会发 `OPTS UTF8 ON`，本服务器支持并自动切换）。

**3. 上传/删除提示 550**
看是不是开了 `--anon`（匿名只读）或 `--readonly`；也可能是目标文件正被别的程序占用。

**4. 端口被占用**
报 `cannot bind port`，换 `--port 2122` 之类，或先查谁占了：
```
netstat -ano | findstr 2121
```

**5. 关掉窗口服务就没了**
正常。想让开机自动起，可以用「任务计划程序」建一个登录时触发的任务，程序填 `ftpsrv.exe`，参数按需要填。

**6. 手机/客户端报 `java.net.SocketException: Software caused connection abort`（"连接被中止"）**

这是**客户端那一侧的 TCP 被中断了**，不是服务器拒绝了它 —— 服务器拒绝会给出正常的 FTP 错误码（`530` 登录失败、`425`/`426` 数据连接问题等），不会是这种底层 socket 异常。常见原因按概率排：

1. **手机网络变了/睡过去了**：Wi-Fi 切频段、切到流量、锁屏后系统挂起网络、App 被切后台被限制 —— 安卓会直接把这个 socket 掐掉，App 下一次读写时就报这个错。
   手机端建议：把该 App 加入**电池优化白名单/允许后台活动**，传输时别锁屏，别中途切 WiFi。
2. **控制连接空闲太久被服务器回收**：本程序默认空闲 **900 秒**（15 分钟）没有命令就关闭控制连接，关闭前会先发一条 `421 Idle timeout` 给客户端。设置里能把「空闲超时」调大（最大 86400 秒）。
3. **路由器/NAT/AP 掐掉了空闲连接**：这正是 TCP 保活要解决的，默认 30 秒探测一次；路由器特别凶就调成 15。
4. **客户端自己的毛病**：一些老 App（targetSdk 很旧、跑在 Android 13+）会自己把 socket 关掉还继续写，堆栈里能看到 `close()` 和写操作连在一起。

**怎么确认是谁断的 —— 看服务器日志**，现在每条会话结束都会写清原因：

```
[21:48:49] connect: 192.168.1.31
[21:50:11] disconnect: 192.168.1.31 (QUIT)                                      <- 客户端正常退出
[21:50:11] disconnect: 192.168.1.31 (idle timeout 900 s, last command: PWD)     <- 服务器按空闲超时关的
[21:50:11] disconnect: 192.168.1.31 (connection lost, last command: RETR a.mkv) <- 链路或客户端断的
[21:50:11] RETR a.mkv aborted after 1234567 bytes (socket error 10054)          <- 传输被打断，带错误码
```

Winsock 错误码对照：`10053` 本机软件中止连接 / `10054` 对端强制关闭（RST）/ `10060` 超时 / `10058` 连接已关闭还在发。

**7. 手机端用「MT管理器 / ES / Cx」这类 App 自带的 FTP 客户端，传几 MB 就断**

日志里的长相：几秒内刷出十几条

```
[23:50:50] RETR 电影.mkv (192.168.1.13)
[23:50:50] RETR 电影.mkv aborted after 1310720 bytes (socket error 10054)
[23:50:50] RETR 电影.mkv (192.168.1.13)        <- 立刻重来
...
```

**原因**：这类客户端带一个「**多线程传输**」开关。打开后它会把一个文件切成几段、并发去拉，**每段拉完直接把连接掐掉**（不发 QUIT、不发 ABOR），服务器只能记成 `10054`（对端 RST）。所以「aborted」不等于服务器出错，是客户端用完就走。真正的问题是它掐得太急、重试太密（实测 4 秒内 38 条命令 / 3 条控制连接），把服务器当跑步机用。

**怎么办**：进客户端自己的 **FTP 设置 → 关掉「多线程传输 / 多线程下载」**，改成单连接。单连接时我们这边实测 40 MB 一次传完没问题；几个 GB 的连续上传也都稳定。

**怎么确诊**：
- 日志里出现 `resume=数字` → 客户端在做**断点续传 or 分段下载**（它先用 `REST 数字` 跳到中间再拉）。
- `aborted after N bytes` 里 N 是 **262144 的整数倍** → 正好是我们的发包块，说明是刚发完一块就被对端掐掉，不是服务器写错。
- **本版已降噪**：小于 8 MB 且由客户端主动断开（10053/10054）的下载，只记一行
  `RETR x: 1.02 MB, client closed early (verify/thumbnail read - not an error)`，不再刷 `[aborted]` + 错误码两行。
- 顺带一提：这种「连了又不要」的连接会滞留在被动端口队列里，服务器现在会自动识别并丢弃它们（日志里写 `dropped a stale data connection from ...`）。

**8. 客户端报 `Read timed out`（"读取超时"），任务变成"上传文件到 ftp@x.x.x.x 时出现错误"**

`Read timed out` 是 Java 客户端的**读超时**：它把一条命令发出去，等服务器回话，等过头了（多数 App 设 30 或 60 秒）就直接判任务失败。也就是说——**问题不在数据传得慢，而在某一句回复来得太晚**。

服务器这边唯一可能"回复很晚"的地方，就是上传结束、准备回 `226` 之前的那一步：早期版本会先 `FlushFileBuffers`（强制把文件刷到盘上）再回 `226`。**一个 3.9 GB 的文件在机械盘上强制落盘要几十秒**（缓存里攒着的脏页要真的写进盘），客户端等 226 等到超时，任务就失败了。

现在改成：
- **默认不落盘**，收完数据立刻回 `226`（Windows 的写缓存会自己把数据写下去，正常关机/关程序都不会丢）；
- 想要"落了盘才算成功"的，去设置页「其它 → 传输完成后强制写入磁盘」勾上（命令行 `--flush`）——只在 SSD 或小文件场景下建议开。

顺带一提：如果共享的是**外接硬盘**，硬盘空闲休眠后再访问会有几秒的唤醒等待，也可能让客户端觉得"没回应"。传大文件期间硬盘是不会睡的，一般不影响。

**怎么区分是哪一种超时**：
- 日志里 `STOR x` 之后很快出现汇总行、但客户端还是报错 → 看客户端自己的设置（多线程、超时秒数）。
- 日志里 `STOR x` 之后隔了很久才有汇总行 → 就是盘慢（落盘/写入）导致的，别勾"强制写入磁盘"。
